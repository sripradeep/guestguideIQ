### Findings

1. **AC1.1.4 — testable, but missing a negative path.** The AC covers only the case where the signup domain maps to an existing locality-brand. It never states what happens when a Property Owner signs up through a domain/subdomain that is *not* associated with any locality-brand (e.g. a stale, mistyped, or not-yet-provisioned domain, or the bare central domain if one still resolves at all). Given US1.1's own new dependency line ("US4.4 — a locality-brand must exist before signup through its domain is possible"), the unmapped-domain case is a real, reachable failure mode, not a hypothetical — it deserves the same treatment as AC1.1.2/AC1.1.3's other signup failure paths.

2. **AC4.4.2 has a GWT structural gap, not just a missing case.** As written — "Given a locality-brand's domain configuration, when I register or update it, then the change is managed centrally by GuestGuideIQ ops — no Property Owner or third party can alter it" — the Given/When describe ops's *own* action, but the Then asserts something about a *different* actor (Property Owner/third party) who never appears in the setup. That clause isn't independently verifiable from this AC as phrased; there is no scenario here where a non-ops actor actually attempts the action and is rejected. This needs to be split: (a) ops successfully registers/updates domain config (keep as-is, minus the "no one else can" clause), and (b) a new, explicit negative/authorization AC — e.g. "Given a Property Owner (or other non-ops actor) attempts to alter a locality-brand's domain configuration through any interface available to them, when they attempt it, then the action is rejected or the capability is unavailable to them." Without (b), FR9.5's authorization boundary is asserted in prose but not actually given a pass/fail test.

3. **US4.4 is missing a domain-uniqueness negative path.** None of AC4.4.1–4.4.3 covers what happens when ops tries to associate a domain that is already assigned to a *different* locality-brand. Given FR9.4/FR9.5 (centrally-managed, potentially many custom domains and subdomains) and FR8.6/NFR6.1 (routing depends on unambiguous domain→locality-brand resolution), a domain collision is a realistic and consequential failure mode — misrouting one locality's traffic/branding into another's. This is the same class of gap as the duplicate-username check in AC1.1.2 and the duplicate-POI check in AC4.1.2; US4.4 should have an equivalent, e.g.: "Given a domain that is already associated with another locality-brand, when I try to associate it with this locality-brand, then I see a clear validation error and the existing association is undisturbed."

4. **AC1.5.3 / AC2.2.3 — testable boundary is acceptable, and a fallback-rendering concern is already pre-empted upstream.** Both assert "renders using my property's locality-brand" — clear enough as an epic-level pass/fail (compare rendered branding against the locality-brand record associated with the property/domain). I considered flagging a missing fallback state for a locality-brand with incomplete visual styling, but AC4.4.3 already requires a locality-brand to be rejected at creation time if its identity data is invalid/incomplete, so every persisted locality-brand should have the minimum data these two ACs render from. Not raising this as a separate objection given that upstream guard already exists — flagging only so domain-design confirms the two are actually linked (AC4.4.3's validation must cover whatever minimum fields AC1.5.3/AC2.2.3 render).

5. **AC2.1.4 — testable, no additional negative path needed here.** "Resolves through that property's own locality-brand domain/subdomain — I never see... a central domain" is a clear, observable pass/fail (check the resolving domain matches the property's locality-brand). The deeper "what if resolution is ambiguous/misconfigured" question is legitimately NFR6 territory (see below), not something this epic-level AC needs to re-litigate.

6. **Traceability — FR9 row is genuinely earned by 4 of 5 stories directly, and defensibly (not a stretch) by the 5th.** US4.4 (AC4.4.1→FR9.1/FR9.4, AC4.4.2→FR9.5), US1.1 (AC1.1.4→FR9.6), US1.5 (AC1.5.3→FR9.3), and US2.2 (AC2.2.3→FR9.2) each carry an explicit, direct FR9.x tag in their own AC text — no overclaim. US2.1's contribution is via AC2.1.4, tagged `[FR8.6]` rather than a direct FR9.x ID — technically FR8.6 lives under the FR8 heading, not FR9. However, FR8.6 itself explicitly cross-references "per FR9.4/NFR6.1," and the document already uses this same indirect-linkage convention elsewhere (the FR3 coverage row lists US1.1 via its FR3.5 tag, and FR3.5 itself cross-references FR9.6) — so this is a consistent, established pattern in this artifact, not a one-off stretch. Not blocking, but worth naming explicitly so a future reviewer doesn't mistake it for a tagging error.

7. **FR9.7 correctly requires no AC.** FR9.7 states locality-brand assignment is fixed at signup and reassignment is out of scope "unless raised again" — a negative-scope statement (no feature to build), not a positive requirement needing a pass/fail AC. Its absence from any AC in the delta is correct, not a coverage gap.

8. **NFR6 — "Deferred" status correctly names an owner and does not silently drop the requirement.** `target: "domain-design/infrastructure-design (multi-tenant domain routing mechanics)"` follows the same explicit-owner convention already used for NFR1–NFR5, and is consistent with how the FR9-adjacent ACs (AC2.1.4, AC1.1.4) describe only the *observable* behavior (guest/owner sees the right brand on the right domain) while leaving the *resolution mechanism* itself (how an incoming request's domain is matched to a locality-brand, TLS/cert provisioning per NFR6.2) to the deferred stage. No gap here.
